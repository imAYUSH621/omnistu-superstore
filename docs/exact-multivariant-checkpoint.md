# Exact multivariant order-line increment

Based on exact draft PR274 head a126c2158d02b61f90cb179abe6a490771b60d60. No hosted application, production promotion, supplier/account request, payment or mail activation.

OrderItem previously used (orderId, productId) as its primary key, collapsing or refusing two variants of one parent. A migration adds a lineKey and changes that primary key to (orderId, lineKey). Every historical row receives deterministic legacy:<old productId> identity while keeping its existing values. This is not a supplier/variant backfill. Unbound future ordinary lines receive an independent generated key. Exact supplier-bound preparation explicitly stores its independently validated approved line key. No existing row, paid state, quantity, price, name or source evidence is deleted or rewritten. Hosted application still requires the original scoped authority, backup, schema dependency review and validation, not local proof alone.

New persisted plans identify their exact line-key model. The payment/settlement loader matches each item by exact line key, parent, quantity and price, supporting multiple variants of a parent without conflating them. Older immutable one-variant plans retain their existing product-key compatibility and cannot acquire additional inferred variants. Qualified simulation receipts retain their existing exact line identities in the ordinary display projection.

A real disposable-DB test selects Red and Blue from one parent, stores two distinct ordinary item rows at10/15USD, binds explicit synthetic2.75shipping/1.25tax, calls the actual mocked PayPal create/capture actions at29USD, and consumes both allocations. Parent stock deliberately remains0. Altering only an order-line key is refused before any mocked provider creation. This is source/transaction integration, not a real payment or supplier acceptance.

Provider/mode/warehouse eligibility is now a shared pure projection invoked before payment as well as dispatch. Unsupported provider, CJ mode other than exact-warehouse mode1, missing origin or mixed shipment tuple cannot first accept payment and fail only at dispatch. The parent-product stock precheck no longer overrides an independently validated exact allocation on the bound path; legacy unbound behavior remains unchanged.
