# Paid-order supplier binding: gated engineering increment

Production dispatch must remain OFF. Nothing in this change approves commercial terms, payment activation, supplier purchases, emails or supplier funding. Existing unbound orders are not backfilled. Current production still has no sale-qualified product.

This change replaces independent automatic/manual routing with a single persisted paid-order plan. The operator endpoint accepts only an existing order UUID; caller mapping and address overrides are rejected. Slug-derived provider choice and default supplier SKU, variant, origin, method and state are removed. Both entries reload the same immutable order-bound plan and exact internal allocation before supplier submission. Unsupported suppliers and mixed shipment modes require review. Disabling dispatch returns OFF without inferring a supplier.

The additive migration creates immutable OrderSupplierPlan, internal OrderSupplierAllocation and durable OrderSupplierAttempt records. No hosted migration is applied. A conditional least-privilege backend migration targets only the existing omnistu_app identity. It does not create a login, grant anonymous/customer access, grant offer publication/quote writing, or enable a feature. Preparation is server-only and is not exposed as a live checkout action. It atomically reads the owner's selected qualified cart, checks current published exact offers, writes ordinary order items plus an immutable source-bound tuple, reserves internal offer quantity and clears that cart. Replay returns one order. Multiple variants of one parent product are explicitly refused because the existing OrderItem primary key cannot represent them. Nonzero shipping/tax amounts are explicitly refused rather than inventing a policy. The commercial-terms source is stored with the approval evidence.

Required real-payment paths validate HELD allocation before PayPal create/capture or Stripe intent/retrieval. Paid settlement consumes allocation atomically rather than decrementing generic parent stock. Dispatch requires paid state and CONSUMED allocation. Historical unbound production orders enter review, without guessed mapping. Snapshot hashes retain compatibility when the new optional CJ origin/mode fields are absent.

CJ projection uses exact VID, destination address, origin, warehouse, mode and freight method. Only platform-logistics mode1 is accepted because the API documents storageId for that mode; merchant-logistics mode2 cannot prove the exact warehouse and is held. It uses payType3, which creates an UNPAID supplier order only. It does not pay, fund or dispatch a shipment. A durable attempt marker precedes any external call. Concurrent or repeated requests cannot resubmit or authenticate again. Malformed, rejected, timed-out and uncertain outcomes require review and are not automatically retried. Current code is not a verified live CJ integration.
